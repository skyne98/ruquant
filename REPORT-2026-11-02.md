Prefill (pp512): Q4_0 287 t/s, W4A4 364 t/s. Plain decode without a drafter (tg128): Q4_0 27.0, W4A4 27.7 t/s.
At one token per pass both are bandwidth-bound; W4A4's gain is in multi-token passes.

The W4A4 matmuls are bit-exact with the CPU reference on the MI50 (test-backend-ops, 58 shapes).
How they got fast:
- `v_dot8` skinny kernel with an in-place weight repack on first use, plus a fused epilogue and split-K fixup;
- tiled Paley stage for the online Hadamard;
- launch shape from a sweep: 8 waves, 4-way split-K.

Spec decode (llama-server, chat prompts, greedy, 256 tokens, 4 prompts):
- DFlash2 (incoai) beats DSpark here: about 45-69% acceptance, mean accepted length up to 4.4.
- Draft length 5 is best for W4A4. Each extra draft token costs ~4 ms per step.
- The drafter is converted for the rotated target by `ruquant drafter`:
  - R1 is folded into its `fc` input chunks;
  - it gets its own unrotated token embedding;
  - its own lm_head is W4A4H (online Hadamard), and acceptance is unchanged;
  - `--linears w4a4h` also makes its layers W4A4H: small gain.
- Q8_0 `ssm_out` and Q8_0 lm_head instead of Q5_K / q6_K cut a step from 69 to 65 ms. mx's repacked Q5_K
  kernel at 6 columns took 150 µs per call. Both types are more accurate than the ones they replace.
- Backend (GPU) sampling: +1 t/s.
- Sustained 1024-token generations: 55.2 t/s mean, 70.9 t/s on the math prompt; the step time stays at 64.5 ms.

Where a step's ~65 ms goes:
- target W4A4 GEMMs ~23 ms;
- mx recurrent-state `set_rows` and copies ~10 ms;
- drafter ~13 ms;
- activation quantizers ~4 ms;
- Paley ~2.7 ms;
- DeltaNet, norms, attention and the rest ~12 ms.

Per-token activation scales were the largest quality loss left (the simulator put groups of 256 at -17% KLD).
A float scale per group would cost a convert and an FMA per group per output. Instead, every group scale is an
**integer multiple of one per-token unit**, so the whole dot product stays one exact int32:

- per token, R = the widest group range ([min(x,0), max(x,0)] x clip), unit u = R / (15 x 255);
- per group g, multiplier m_g = ceil(range_g x 255 / R) in 1..255 (scale m_g u) and a zero point z_g;
- total = sum_g m_g (acc_g + (8 - z_g) colsum_g), y = (fp32(total) u) s_w, exactly as before per token;
- the kernel starts each group's accumulator at (8 - z_g) colsum_g (weight column sums per group, stored in the
  repack slack as int16) and folds it with one multiply-add at the group's end. Every factor fits 24 bits, so both
  are full-rate `v_mul_i32_i24` / `v_mad_i32_i24`: with plain `*` the compiler emitted quarter-rate
  `v_mul_lo_u32` and 64-bit `v_mad_u64_u32`, which roughly doubled the VALU work at groups of 64;
- CPU and GPU stay bit-identical (test-backend-ops, 56 shapes at tolerance 0, on the 3090 and the MI50, for each
  group size). Group size is `RQ_ACT_GROUP` = 256 (default), 128 or 64 for now.

A symmetric variant (no zero points, no column sums) was tried first and was worse than per token (KLD 0.080-0.094):
the simulator's groups were asymmetric, and the zero point is what pays.

### Weight scales: learned per row, or per group

The simulator (`accuracy/eval_w4a4.py --recipes`, Hadamard R1 + GPTQ, clip 0.9, activation groups of 256 unless
named; 16 chunks against UD-Q8_K_XL; new recipes in `RECIPES`):

| recipe | KLD | top-1 |
|---|---|---|
| a256: activation groups of 256, one weight scale per row | 0.0706 | 88.92% |
| a128 / a64: activation groups of 128 / 64 (clip 0.9 everywhere, which is low for 64) | 0.0680 / 0.0680 | 89.18 / 89.66% |
| a256-ls / -ls2: learned row scales, 1 / 2 rounds of a least-squares refit under H, GPTQ again after each | 0.0716 / 0.0688 | 88.77 / 89.47% |
| **a256-w256: a scale per row per 256 inputs, as integer multiples (1..15) of a row unit, act-order GPTQ** | **0.0618** | 89.37% |
| a256-w256-ls: the same with a refit | 0.0643 | 89.44% |
| a128-w128: both groups of 128 | 0.0660 | 89.21% |

- Learned row scales (the closed-form least-squares scale for GPTQ's codes, `ruquant convert --refit N`) are within
  the noise: GPTQ's clip-search scale is already close to optimal for a whole row.
- Weight groups pay: -12.5% on top of activation groups. They use the same exact-integer trick: block b of a row
  has scale k_b v (k_b in 1..15, v = the row's largest block scale / 15), so total = sum_g k_b m_g S_g. The scales
  are fixed before GPTQ from each block's clip search (GPTQ's static groups), so act order stays; the old float
  group recipe (natural order) reached 0.0652.
- Block format: d = v, sum = 1 << 30 | k_b (`RQ_W_MULT`). Older files keep the row's code sum there, which reads as
  k = 1: the existing model scores bit for bit as before (KLD 0.052692 at groups of 64).
- Kernel: the multiplier per (block, row) is repacked next to the column sums (int16); the fold becomes
  `tot += (k * m) * S` with two full-rate 24-bit ops (k m <= 3825, |S| <= 2^15). Bit-exact on both GPUs with
  weights whose block scales differ (the test now scales weight blocks x1/4..x4; ignoring k fails 56/56 shapes).
- **Overflow, found and fixed.** With multipliers up to 15 the int32 total did wrap: one chat prompt (the
  `prof_spec.sh` train question) produced garbage from the first token, with or without the drafter, while wikitext
  and the 30 acceptance prompts were fine. A rotated massive activation is flat (R1 spreads it over every channel)
  and lines up with a few weight rows, exactly the case where k m sum |c| |q - z| reaches K x 8 x 15 x 255 x 15.
  - int64 totals fixed it but cost 7-14% of a T = 8 forward and collapsed prefill (pp512 82-116 t/s): 64-bit
    accumulators double the registers of the 64-token kernel.
  - The kept fix stays in int32: each group's term k m S (< 2^27) goes in as term >> 4 (`RQ_TERM_SHIFT`), and the
    epilogue multiplies fp32(total) by 16 (exact). The worst case at K = 32768 is then under 1e9, and the dropped
    bits (< 16 units per group) are ~1000x below the quantization noise. The CPU spec shifts the same way.
  - A shift is not linear, so a group must be folded by one wave: K is now split across waves and split-K
    workgroups in whole activation groups (2 steps at G = 64).
  - test-backend-ops now has flat weight rows and tokens with a weight row's signs: |total| reaches 3.5e9 before
    the shift at K = 17408, and truncating the old way fails those shapes.

### Why HIP graphs lose on box 1 (ROCm 5.7)

Measured with `rig/hipgraph_bench.cpp`, `rig/hipgraph_args_bench.cpp`, ROCclr's packet log (`AMD_LOG_LEVEL=4`) and
new graph counters in `GGML_CUDA_HOST_PROF`:

1. **ROCm 5.7 replays a graph as ordinary launches.** `hipGraphLaunch` writes the same AQL packets as direct launches
   (header 0xb02, agent-scope fences, same kernarg pool, no completion signals, no barriers in between) and pays the
   same per-node host cost (0.7-1.7 us). Queued ahead of the GPU, a replay runs exactly as fast as direct launches
   (2000 kernels of 1.6 / 6 / 46 us: identical). So a graph can only save ggml's own per-node work, never the
   runtime's.
2. **It stalls before the first kernel**: it passes over every node before submitting any, about 0.4 us per node
   (first kernel after 47 / 182 / 745 / 1708 us for 100 / 500 / 2000 / 4000 nodes; direct 12-26 us). A whole forward
   (~2100 kernels) starts ~0.8 ms late.
3. **Kernel arguments contend between threads.** With 18-argument kernels (ggml's are like that) a replay costs
   1.1-1.3 us per node alone and 2.6-3.5 us with four threads replaying on four GPUs; with 1-argument kernels four
   threads cost almost nothing extra (0.83 -> 1.04 us). Direct launches degrade too, less (18 arguments: 1.69 -> 3.23
   us). The count of arguments matters, not their bytes (one 80-byte struct scales).
4. **One GPU**: the forward is GPU-bound (host ~9 ms, GPU ~43 ms), so a graph has nothing to save and (2) costs:
   with graphs really on, T = 8 is 176.6 +- 7.1 t/s against 185-186 direct. ggml captured once, instantiated once
   (6.1 ms) and replayed (2.5 ms of host per forward) - no re-capture involved.
5. **TP = 4** (mx's whole-token graphs): captured once, never re-captured, but the four lanes' graphs were launched
   from one thread, 3.6 ms each, so the last lane started ~11 ms after the first and every all-reduce barrier made
   the others wait: 200 t/s against 292 direct. Launching them from the four lane threads (now in the patch) only
   reaches 215-219 t/s, because of (3): each launch then takes 9.1-9.7 ms.
6. **A trap in the test itself**: ggml disables graphs when `GGML_CUDA_DISABLE_GRAPHS` is set to anything, `0`
   included, so comparisons that set it to 0 ran without graphs (night 1's "HIP graphs did not help" may be one).

Graphs win where the runtime turns a replay into less work than the launches it records (CUDA submits pre-built
work). ROCm 5.7 does not. ROCm 7.2.4 does, on the same gfx906 cards, from a user-space install (`rig/rocm72/setup.sh`):

| 2000-kernel chain, one MI50 | ROCm 5.7 | ROCm 7.2.4 |
|---|---|---|
| `hipGraphLaunch` host time | 2054 us (1.03 us/node) | 36 us (0.02 us/node) |
| first kernel starts after | 745 us | 28 us |
| GPU time per kernel, replay (direct) | 2.40 us (1.73) | 1.21 us (1.73) |
| replay with 4 threads, 18-argument kernels | 3.53 us/node | 0.03 us/node |

### Afternoon 2026-11-03: the -sm layer memory fault, and pipelined prefill

Every `-sm layer` run on box 1 faulted ("Memory access fault by GPU node-2 ... Page not present"), with any model
(Q4_0 too), at prefill and decode, with or without fine-grained PCIe. With every HIP call serialized and logged
(`AMD_LOG_LEVEL=3 AMD_SERIALIZE_KERNEL=3 AMD_SERIALIZE_COPY=3`) the fault came from the only synchronous `hipMemcpy` of
the run: 20 KB (one token's embedding row) from the host into a buffer `hipMalloc`'d on GPU 0, issued while GPU 1 was
the current device. mx's `ggml_backend_cuda_cpy_tensor_async` copies host inputs on HIP with a synchronous
`cudaMemcpy` (CUDA uses the destination's stream) and never set the destination's device; ROCm runs a synchronous
copy on the current device, which cannot map another GPU's memory. The scheduler copies the CPU-side token embeddings
to the first layer's GPU this way, so layer split always hit it, and `-sm tensor` never did. The fix sets the device
first (mx's own code, not ours; the pinned upstream has no such path). `-sm layer` on 4 GPUs is now bit-identical to
one GPU (KLD 0.047983, same PPL).

With the prompt in several micro-batches in flight across the four GPUs (llama.cpp's pipeline parallelism, -b >
-ub), layer split prefills faster than TP = 4, with no all-reduce at all:

| layer split, ubatch 128 / 256 / 512 / 1024 | 702 / **1272** / 1048 / 770 | - / **1426** / 1280 / - |
| TP = 4 + RCCL, ubatch 2048 | 950 | 943 |

- **The GPUs never wait on the host.** Kernels run back to back on every lane from the first to the last (0.0 ms
  idle inside the forward). The forward time is all GPU kernel time.
- **The all-reduce is 84% of TP2's excess and 80% of TP4's.** 127 all-reduces per forward, each 512 x 5120 f16
  (5.24 MB): 1.33 ms at TP2, 1.87 ms at TP4. Both ranks enter and leave each one together: the start and end offsets
  between GPUs are the same ~0.3 ms, a timestamp offset, not waiting. So the kernel time is pure transfer. The
  11-03 standalone benchmark (`rig/measured/mi50x4-rocm57/tp.json`) gave 1.07 ms for 4.19 MB at TP2, which scales to
  exactly the 1.33 ms seen inside the forward.
- **The transfer runs at the platform's best rate.** RCCL picks its shared-memory transport (`via SHM/direct/direct`):
  each GPU writes into pinned host memory and the other reads it, ~3.9 GB/s each way at TP2 against 5.2 GB/s for
  one-way peer copies. RCCL's peer path is worse here (`NCCL_P2P_LEVEL=SYS`: TP2 690 -> 646, TP4 882 -> 723; it also

  20 KB per token per stage boundary instead.
- **The alpha/beta projections don't shrink.** `ssm_alpha` and `ssm_beta` are f32 [5120 x 48] and go to rocBLAS

  work itself is ~0.25 GFLOP per call, tens of microseconds on this GPU.
- **Replicated small ops** (the activation quantizer for column-parallel inputs, rms_norm and residual adds on the

- **With the all-reduce skipped** (a temporary `GGML_TP_AR_SKIP` hack, reverted), TP2 is 929 t/s and TP4 1631 at
  pp2048. That is the ceiling for hiding the all-reduce behind compute: RCCL runs on 2 workgroups (2 of 60 CUs),

- **2 stages x TP2 on 4 GPUs (`-tps 2`) runs at TP2 speed** (pp2048 625 / 662 / 712 at ubatch 256 / 512 / 1024):

- **Box 2** (no peer access) has no fast path at all. Its TP2 pp512 of 318 t/s is ~1610 ms per forward; with this

second stream; ceiling above, TP4 pp2048 953 -> up to ~1600); a split-K kernel for the 48-row f32 projections
(-50 ms per forward on every GPU count: ~+5% one GPU, +7% TP2, +10% TP4); fewer all-reduce bytes (reduce-scatter,
then all-gather the next layer's int4 activations instead of f16 hidden states); sequence-parallel norms and
quantizer (~10-18 ms).

### 2026-11-04: a quantized prefill all-reduce (box 1)

Prefill-sized all-reduces can travel as quantized blocks with their own scales instead of f16
(`GGML_NCCL_AR_WIRE=q4_0 | q4_1 | q5_0 | q8_0 | q4_K | q5_K`, mx `ggml-cuda.cu` + `ar-quant.cu`):
1. Each rank quantizes its partial sum and sends chunk j to rank j.
2. Rank j adds the others' dequantized chunks to its own exact chunk, quantizes the sum
   (`GGML_NCCL_AR_WIRE_AG`, default the same type) and all-gathers it.
3. Every rank, rank j too, dequantizes the gathered bytes, so all ranks hold the same values.

Notes:
- Only tensors of at least `GGML_NCCL_AR_QMIN` elements (default 262144, ~51 tokens) are quantized. Decode and
  DFlash2 verify batches keep the f16 wire.
- Per rank this moves 2 (N-1)/N of the quantized size; q4_0 / q4_K need 0.56 B per value where the f16 ring needs 2.
- `GGML_NCCL_AR_ALGO=ag` all-gathers every rank's whole quantized partial instead and adds the others' to its own
  exact one. At N = 2 that is the same bytes in one collective with half the error, but the ranks' copies of the
  prefill hidden state then differ slightly. `agq` sums all dequantized partials in rank order, so the copies match.
- The k-quants get a GPU quantizer: 8 threads per 256-value super-block, sub-block scale and min from min/max,
  without the CPU quantizer's search.
- A round trip against ggml's CPU dequantizers is exact for every type (relative RMS error on Gaussian data with
  outliers: q4_0 13.9%, q4_K 9.8%, q4_1 9.8%, q5_0 6.9%, q5_K 4.8%, q8_0 0.9%).
- ggml's own `quantize_f32_q4_1_block` produced garbage on ROCm 5.7 (KLD 12; its `dm.x = d` stores wrong scales
  here), so q4_1 has its own quantizer.

KLD against UD-Q8_K_XL (16 chunks; one GPU 0.0480):
- "all tokens" quantizes every prefill all-reduce of the perplexity run.
- "context" (`GGML_NCCL_AR_QCYCLE=510,254`) quantizes only the two unscored context ubatches of each chunk and
  keeps the scored ones on f16. That is the real use: a prompt prefilled on the quantized wire, then tokens decoded
  on f16.

### 2026-11-04: where to pipeline and go async (box 1, code reading plus measurements)

How mx runs TP today:
- Each lane issues its subgraph and then the all-reduce closure on the same HIP stream
  (`ggml-backend-meta.cpp`, `per_subgraph_dispatch`). The host never waits inside a forward, the GPUs never idle,
  and nothing overlaps the all-reduce.
- ggml-cuda already has per-stream memory pools and a "current stream" switch (`curr_stream_no`), so a second
  stream for communication is mostly plumbing.
- A DFlash2 step is strictly serial (draft, verify, read back, accept, inject the taps into the drafter), and the
  next draft needs this verify's hidden states.

Server prompt processing, TP4, a 2077-token prompt (third of three runs; llama-bench pp2048 is 1119 / 1324 t/s at
ubatch 512 / 2048):

| server | no drafter | DFlash2 on GPU 0 |
|---|---|---|
| defaults (ubatch 512, context checkpoints on) | 937 | 845 |
| `-b 2048 -ub 2048` | 1078 | 960 |
| `-b 2048 -ub 2048 --ctx-checkpoints 0` | **1228** | **1066** |
| ubatch 512, `--ctx-checkpoints 0` | 1067 | 956 |
| DFlash2 split over 4 GPUs (`-tpsd 4`), defaults | | 805 (decode 37 vs 46 t/s) |

TP2 at the defaults: 694 without the drafter, 634 with it.

What each costs, and what would hide it (measured, or estimated where marked):

1. **Server ubatch 512: -15%.** `-b 2048 -ub 2048` is a flag; prefill only.
2. **Context checkpoints: -12 to -14%.** The checkpoint taken before the last prompt batch drains the pipeline and
   copies the current DeltaNet state (~150 MB) layer by layer through host memory (`create_checkpoint`,
   `llama_memory_recurrent::state_write`). `--ctx-checkpoints 0` removes it, but also the rollback points that let
   a later request reuse a prompt prefix it diverges from (multi-turn chat with reasoning stripped).
   - Fix: copy the state into VRAM or a pinned buffer on a side stream behind an event, and wait only on restore.
   - `LLAMA_NO_MIDPROMPT_CKPT=1` exists but keeps exactly this near-end checkpoint.
3. **DFlash2 taking in the prompt: -13%** (1228 -> 1066, ~250 ms for 2077 rows). The drafter encodes all prompt
   taps after the target finishes (deferred encode; an earlier flush with `LLAMA_DSPARK_FLUSH_ROWS=512` changes
   nothing).
   - The taps travel GPU 3 -> host -> GPU 0. That is 5 layers x 2077 x 5120 x 4 B = 212 MB each way, ~70 ms
     (estimate), although lane 0 already holds the same mirrored data. A device copy removes it.
   - The encode itself then runs while GPUs 1-3 idle. Overlapping it with target prefill shares GPU 0 with lane 0,
     so it pays only where GPU 0 has idle time.
4. **Prefill all-reduce: ~10% (TP2) / ~19% (TP4) of a llama-bench forward** on the q4_K wire (the ceiling with
   all-reduces skipped is 929 / 1631 at pp2048).
   - Fix: split the row-parallel matmul that ends each all-reduce subgraph (ffn_down, attn_output, ssm_out) into
     token chunks, and run chunk c's all-reduce on a second stream while chunk c+1 computes.
   - The producing matmuls take about as long as the all-reduce, so most of it hides (estimate +12-15% at TP4,
     +6-8% at TP2).
5. **DFlash2 step host path: ~4-5 ms of a ~50 ms 1-GPU step** (rocprof). At TP4 (~40 ms) it is larger:
   - (a) TP turns off GPU sampling, so every step reads back all 8 positions' logits (8 x 248k x 4 B = 7.9 MB from
     4 GPUs) and scans them on the CPU. A per-lane argmax and a 4 x 8 merge would save ~1.5-2.5 ms (estimate).
   - (b) The drafter's inject and draft batches share one graph-reuse slot, so its graph is rebuilt twice per
     step (the 0.3-1.3 ms gap in the trace). Separate slots fix it.
   - (c) The taps reach the drafter through the host after a full sync of the 4 target GPUs. A device copy from
     lane 0 behind an event lets the inject overlap the target's lm_head and logits copy (~1 ms).
   - (d) Token streaming and the server queue round trips run before the next draft is launched (~0.3 ms).
   - Together, an estimated +8-15% DFlash2 t/s at TP4.
6. **Not worth it:**
   - Splitting the drafter over the TP group (`-tpsd 4`: decode 37 vs 46 t/s, prompt 805 vs 845).
   - Overlapping draft and verify at batch 1 (DFlash2 needs the verify's hidden states).

| TP4 attn.o (K 1536) | 5.4 + 3.7 + ~7 = ~16 us | 4.8 + 6.9 = 11.7 us |

On one GPU the kernel saving (~0.8 ms per forward) passes straight through. At TP4 about 60% of it does, as with the
skinny-kernel slowdown above.

How it got there. Each step was measured, and its cause found in the ISA, before the next one:
1. **One kernel, one 1024-thread block per token: 4x slower** (1 GPU down 175.8 vs 44 us, TP4 56.5 vs 22 us; TP4
   forward 290 -> 273 t/s, one GPU 186 -> 155). Two causes:
   - 8 tokens are 8 workgroups on 60 CUs.
   - The Paley sum with a runtime P costs ~18 instructions per term, with a dynamic mask index and an
     `s_waitcnt lgkmcnt(0)` after every LDS read. The template-P kernel takes ~4 per term.
   - Lesson: keep the expensive Paley part spread over P / 4 blocks per row and P a template parameter. Every block
     redoes the cheap Sylvester part instead.
2. **Two kernels, a wave per chunk: stats 42.7 us against 13.6 for the Paley kernel alone** (fused total 51.0 vs
   43.9 unfused). The Sylvester loop was a runtime loop. Each of a wave's 17 chunks issued its load and waited for it
   (`s_waitcnt vmcnt(0)`), then waited again after each of six dependent `ds_bpermute`s. Roughly 10 us per round of
   workgroups, and one GPU runs ~3 rounds: 17 KB of LDS allows 3 workgroups per CU, and 544 workgroups need 3.02.
3. **Stage-major, all loads in flight first: 28.6 us.** The compiler then kept only two `ds_bpermute`s in flight per
   wave (it reuses their destination registers), so each stage was still LDS round trips.
4. **DPP for butterfly stages 1-8** (quad_perm, and row_ror 4/12/8), `ds_bpermute` only for 16 and 32: 23.8 us.
5. **A row of 16 lanes per chunk, lane t holding values t + 16 q**: stages 1-8 cross the row via DPP and stages 16+
   stay in registers, so no LDS round trips in Sylvester: 22.7 us (TP4 9.6).

What is left over the Paley kernel alone (+9 us on one GPU, +4 at TP4):
- the redundant Sylvester VALU (each of the P / 4 blocks transforms all P chunks);
- the group min/max reductions (12 dependent `ds_bpermute`s per wave);
- the third round on one GPU.

The codes kernel at TP4 (6.9 us) costs nearly what the full quantizer did (7.7). Both sit near the ~4-5 us floor of a
small kernel, so at TP4 the gain is mostly the dropped launch.

### 2026-11-05: whole-token HIP graphs on ROCm 7.2.4 (box 1)

The question was whether HIP graphs can remove the cost of ~2100 small kernels per verify. On ROCm 5.7 they can't: a
replay is sent as ordinary launches (above). On ROCm 7.2.4, AMD's packages installed in user space
(`rig/rocm72/setup.sh`), a replay is pre-built work. There mx's whole-token graphs had replayed a TP4 verify ~2 ms

**Changes (in the patch):**
- Signature-keyed reuse (`ggml-backend-meta.cpp`):
  - when the graph id is new, the meta backend fingerprints the per-GPU graphs: every node's op, parameters, shape

  - an identical recording is replayed instead of re-captured;

  used only while no pool has given memory back to the driver since its capture. This guards the existing same-id
  replay too.
- No input ring for single-stage `-sm tensor` with token graphs (`llama-context.cpp`):
  - The first version still made 52 captures and 4 reuses in 30 requests. The fingerprint dumps of two requests' first
    verify graphs differed only in their inputs (`inp_mixed_embd#3` vs `#0`): with pipeline parallelism on, the
    scheduler keeps 4 input copies and moves to the next one on every graph allocation.

### 2026-11-05: stream-K for the skinny kernel (box 1)

**The idea.** RESULTS.md estimated up to ~6% from stream-K. The premise was that the skinny kernel loses bandwidth to
wave quantization: at TP4 the launches have 56-136 workgroups against ~120 resident.
- Before: each workgroup took one tile (R channel groups) and a fixed 1/G of K.
- `rq_skinny_sk_kernel` (env `RQ_SKINNY_SK=1`) instead splits the launch's tiles × activation groups evenly over a grid
  of resident size.
- Partial tiles meet through LDS and int32 atomics, so the result stays bit-exact. All W4A4 tests pass, including 24
  new cases at the TP4 shapes.

**Result: it doesn't pay.** T=8 forward, median of repetitions 11-30, ms:

| | default | stream-K, 120 workgroups | stream-K, 90 / 100 / 110 |
|---|---|---|---|
| TP4 | 25.28-25.38 | 25.91-25.93 | 25.34 / 25.49 / 25.53 |
| one GPU | 40.24-40.43 | 41.97 | 40.53 / 40.59 / 40.18 |
| TP2 | 30.26-30.29 | 31.37 | |

**Why: kernel times per launch.** These are rocprofv3 kernel traces of single launches (`GGML_CUDA_DISABLE_FUSION=1`;
TheRock's tarball lacks rocprofv3's tool library, `lib/rocprofiler-sdk`, which had to be fetched separately).

| matmul (N × K) | split-K plan: workgroups, us | stream-K grid sweep: workgroups → us |
|---|---|---|
| TP4 qkv+z, 4096 × 5120 (32 tiles) | G=1: 32 → 34.1; **G=2: 64 → 30.7**; G=4: 128 → 35.5 | 32 → 34.7, 64 → 31.7, **80 → 53.1**, 100 → 31.7, 120 → 34.1 |
| TP4 gate+up, 8704 × 5120 (68 tiles) | G=1: 68 → 56.2; **G=2: 136 → 52.8** | 68 → 57.8, **90 → 48.2**, 120 → 49.8, 121 → 57.1 |
| one-GPU attention output, 5120 × 6144 (40 tiles) | **G=1: 40 → 51.2**; G=2: 80 → 45.0; G=3: 120 → 85.0 | 40 → 50.9, 80 → 46.9, **100 → 37.4**, 110 → 37.6, **120 → 86.6** |

The default plan is in bold in the second column.

**What the measurements show:**
- **At the same grid size, stream-K times like split-K.** Its only lever is the grid size, and the device doesn't
  reward more workgroups: 1-2 per CU stream about the same.
- **Power-of-two shares are the trap.** The 2× outliers (80 workgroups for 4096 × 5120, 120 for 5120 × 6144) both give
  every workgroup exactly 32 activation groups. That puts each wave's stream at an 8 KB multiple from its neighbours'.
  - The concurrent streams then line up on the same DRAM channels.
  - A grid one or two off the aligned size runs at full speed: 5120 × 6144 at 119 / 121 takes 39.7 / 44.2 us, against
    86.6 at 120.
  - This was "wave quantization" in the 2026-11-04 section above. That diagnosis was wrong.
- **Shapes win or lose about equally.** Stream-K at a good grid wins on some (TP4 gate+up 52.8 → 48.2 us, one-GPU
  attention output 51 → 37 us) and loses on others (one-GPU DeltaNet qkv+z 92 → 103 us). In the forward they cancel.
- **The waves are latency-bound, so occupancy decides.**
  - Each wave has one step of weights in flight.
  - Loading the next activation group's column sums and multipliers a group early cost 4 VGPRs (64 → 68, so 3 waves
    per SIMD instead of 4), and every shape got 23-28% slower.
  - Larger launches amortize a fixed latency per launch: three 4096 × 5120 matrices in one fused launch take 16 us each,
    against 30.6 us alone.

**What shipped:**
- The kernel's inner loop is now one device function, shared by both kernels.
- The job lookup uses per-field selects in a macro. A helper that took the `rq_jobs` argument by reference copied all
  270 bytes of it to scratch: 128 VGPRs and 352 B of scratch, a 40% slower TP4 forward (35.6 vs 25.4 ms), until found
  in the kernel descriptors.
- The refactored kernel is slightly faster at TP2: DFlash2 98.5 / 97.8 → 99.5 / 99.4 t/s, forward 30.7 → 30.3 ms. TP4
  is unchanged (113.6 / 113.4 → 113.7 / 113.5), as is one GPU (84.2 / 84.4 → 84.5 / 84.7). The tokens are the same.
  The cause of the TP2 gain was not traced; the kernels' scalar register allocation differs.
- Stream-K stays in, off by default (`RQ_SKINNY_SK`, `RQ_SKINNY_SK_SLOTS`).
- test-backend-ops has the TP4 shapes as cases, and W4A4 perf cases at the model's shapes. Perf mode fuses repeated
  matmuls into 3-job launches unless `GGML_CUDA_DISABLE_FUSION=1`.

**What this points at instead:**
- More bytes in flight per wave without more VGPRs, for example deeper weight prefetch paid for by fewer
  accumulators, or LDS staging.
- Split plans that never give a power-of-two number of groups per wave.
- Fewer, larger launches.

### 2026-11-05: what limits the skinny kernel's bandwidth (rocprofv3, box 1)

Every profile is in `profiles/box1`, listed in `profiles/INDEX.md`.

**Tooling on gfx906:**
- TheRock 7.12's tarball lacks rocprofv3's tool library (`lib/rocprofiler-sdk`); it was fetched from the same tarball.
- The gfx906 counter set is thin: no wave-wait counters, no occupancy level, no DRAM read level.
- `ROCPROFILER_METRICS_PATH` takes a copy of `counter_defs.yaml` with extra gfx906 definitions (saved with the
  profiles):
  - the SQ events, at gfx908's numbers minus one past event 26: `SQ_WAVE_CYCLES` 46, `SQ_WAIT_ANY` 57,
    `SQ_WAIT_INST_ANY` 60;
  - `TCC_BUSY` 2;
  - the EA read level, TCC event 49, found by scanning events 36-62. Little's law on it reproduces the measured
    bandwidth: ~1100 EA reads in flight × 64 B ÷ 447 ns ≈ 157 GB/s per EA port, ×2 ports ≈ 313 GB/s, against 306.
- What didn't work:
  - Counters built on `accumulate()` (occupancy, VMEM in flight) crash rocprofv3 on gfx906.
  - The inferred `SQ_ACTIVE_INST_VMEM` (69) reads ~0.

**Counters on the kernel** (single launches, test-backend-ops perf, `GGML_CUDA_DISABLE_FUSION=1`):

| launch | workgroups | GB/s | MemUnitBusy | MemUnitStalled | VALUBusy | L2 hit |
|---|---|---|---|---|---|---|
| TP4 qkv+z 4096 × 5120 | 64 | 311 | 45% | 0.3% | 20% | 6% |
| TP4 gate+up 8704 × 5120 | 136 | 412 | 51% | 0.4% | 27% | 5% |
| one-GPU gate+up 34816 × 5120 | 272 | 528 | 57% | 0.2% | 34% | 2% |
| one-GPU attention output 5120 × 6144, stream-K grid 120 (aligned) | 120 | 180 | 77% | 0.1% | 13% | 7% |

GB/s here is from the counting runs' own cycles. Reading the counters:
- FETCH_SIZE equals the weights plus their column sums and multipliers: nothing is fetched twice.
- Nothing is saturated.
- At 64 workgroups the waves wait 68% of their life (`SQ_WAIT_ANY` / `SQ_WAVE_CYCLES`) and issue VALU work 16% of it.
  DRAM latency is 770 cycles (450 ns), which is not congested, with only ~2200 reads in flight. Peak needs ~2.6× that.
- The aligned grid keeps TA busy 4× longer for the same bytes, the signature of a DRAM channel jam.

**The access pattern alone, as a microbenchmark** (`rig/membench/stream_bench`, the same 1 KB per wave per load):
- **Plain streaming peaks at 800-814 GB/s** with only 240 waves × 2 KB in flight. Bytes in flight are not the limit.
- **Power-of-two per-wave run lengths lose 25-45%** against their neighbours (480 waves): 128 KB 337 GB/s vs 136 KB 592;
  256 KB 463 vs 240 KB 715; 512 KB 551 vs 520 KB 771.
- **The skinny-like pattern** (8 waves per workgroup, two loads in flight, 32 dot8 per load) streams 477 GB/s at 64
  workgroups, 667 at 120 and 597 at 136.
  - Starting each wave at a different offset in its run raises that to 541-575, 728-734 and 633-650.
  - At 64 workgroups the rest is placement: 64 on 60 CUs leaves 4 CUs with two.
- **Launch size costs little once launches run back to back:** a 10 MB launch at 64 workgroups streams 546 GB/s, 9-18 MB
  at 120 streams 650-695. Timed one launch per sync, small launches read 2× slower because the GPU is still leaving
  its idle clocks; that biased the first stride map.

**The kernel's own costs, ablated** (timing-only builds with wrong results; kernel us):

| launch | kernel | no colsum / wk loads | no activation loads | no split-K fixup | none of the three |
|---|---|---|---|---|---|
| TP4 qkv+z 4096 × 5120 | 30.4 | 30.9 | 29.9 | 28.0 | 26.2 |
| TP4 gate+up 8704 × 5120 | 53.0 | 50.6 | 52.2 | 51.7 | 47.8 |
| TP4 down 5120 × 4352 | 28.5 | 27.8 | 28.2 | 27.4 | 24.8 |
| one-GPU gate+up 34816 × 5120 | 174.9 | 160.8 | 173.6 | 171.5 | 157.9 |

What the ablations show:
- On big launches, the per-group column-sum and multiplier loads are the largest single cost (−8% without them).
- The split-K fixup is 2-3 us at TP4; the activation loads hardly matter.
- Even without all three, the TP4 qkv+z launch takes 26 us, against 19 us for the same bytes in the microbenchmark.

**The fix this points at: rotate each wave's K order** (`RQ_SKINNY_ROT`, default 7).
- A wave's sum doesn't depend on the order of its activation groups, so wave i starts its slice at group (i × 7) mod
  its groups and wraps round. The result is bit-exact (all tests pass).
- No VGPR cost: 64 at T=8.
- Kernel times (us), in order → rotation 7:

### 2026-11-06: our q4 KV attention with v_dot8 (box 1)

`ggml/src/ggml-cuda/rq-fattn.cu` in the fork. It is on for q4_0 caches (`-ctk q4_0 -ctv q4_0`) on gfx906, and
`RQ_FA_DOT8=0` turns it off.

**What it covers:** head size 256 and 1-16 query tokens, i.e. decode and the DFlash2 verify. Prefill keeps
llama.cpp's tile kernel.

**The cache:**
- llama.cpp's q4_0 with mainline's Hadamard rotation: rotated int4 with a scale per 32 values.
- A q4_0 nibble q is the signed int4 q - 8 once its top bit is flipped, so a K word feeds `v_dot8_i32_i4` after one xor.
- Nothing is converted to f16.

**The kernel:**
- Q is quantized per 32 values to int4, which is pure dot8 (default). `RQ_FA_DOT8=2` takes int8 Q, split into two int4
  planes (16 hi + lo) at two dot8 per 8 products.
- The KV sequence is split over ~2 workgroups per CU, and each workgroup streams 64-token tiles of K and V through LDS.
- Q·K: lanes are tokens; each wave takes a quarter of the rows (query heads × tokens); Q comes through scalar loads.
- Online softmax per row with DPP reductions; P goes to LDS as f16.
- P·V: lanes are the 256 channels; each lane decodes its channel of V once per token and uses it for every row
  (`v_dot2_f32_f16`, f32 accumulation).
- llama.cpp's combine kernel merges the chunks.

**Correctness:** test-backend-ops cases at the model's shapes (KV head 256, 6 query heads per KV head, q4_0, 1-16
tokens, 256 / 4096 cells).
- int8 Q passes all 8 within the test's NMSE limit of 5e-4 against the CPU (which takes Q as q8_0).
- int4 Q with scale amax / 7 landed at 5.0-5.6e-4, and one of llama.cpp's own q4_0 cases failed with it as the default.
  Q is now rounded as q4_0 rounds, the block's largest value to -8 (16 levels instead of 15).
- With that, all 4001 FLASH_ATTN_EXT tests pass with the kernel on by default. The added cases allow 1e-3, since the
  design takes int4 Q.
- Final build: KLD 0.0434 / 91.14% top-1 at 8-token ubatches (the amax / 7 build gave 0.0423; within the ±3% of 16
  chunks). Speed is unchanged: verify at 64k 59.6 ms, decode 38.5 ms.

**Getting it fast (one GPU, 8-token verify forward at 64k, ms):**

| version | verify at 64k | decode at 64k |
|---|---|---|
| f16 cache, tile kernel | 64.4 | 44.7 |
| stock q4_0 (vector kernel / tile kernel with f16 conversion) | 83.9 | 132.4 |
| v1 | 71.4 | 40.0 |
| v2: DPP reductions, P·V without per-row branches, P of 4 rows in flight | 60.3 | 38.7 |
| v3: the tile's mask in LDS (kept) | 59.6 | 38.5 |
| v4: rows per wave, 4 channels per lane (dropped) | 59.1 | 40.9 |

- **v1 lost to f16.** The runtime row guard (`if (r < R)`) in the unrolled 48-row P·V loop compiled to one branch per
  row. Each row read its P from LDS, waited for it, then ran 4 dot2. The 48 branch masks also spilled scalar
  registers into VGPR lanes (199 `v_readlane`). On top of that, `__shfl_xor` became `ds_bpermute`, 12 waited LDS
  round trips per row and tile.
- **v3, rocprofv3 counters at 64k:**
  - 1.22 ms per call (16 per forward);
  - VALU busy 50%, waves waiting 54% of their life;
  - 3.7k VALU and 558 LDS instructions per wave and tile, 64 GB/s of memory.
  
  At 112 VGPRs and ~30 KB of LDS, 2 workgroups share a CU, too few waves to hide LDS and memory latency.
- **v4 tested the LDS-bandwidth theory.** It cut the P reads by 4× and gained 0.5 ms; it lost 2.4 ms in decode, where
  6 rows can't amortize decoding V for 4 channels per lane.

### 2026-11-06: INT4 tensor cores on NVIDIA (3090)

For testing on the 3090, and on any NVIDIA GPU that has them (Turing, Ampere, Ada; Hopper and Blackwell dropped INT4
MMA), the W4A4 matmuls and the q4_0 attention's Q·K now run on the INT4 tensor cores. Before, the 3090 ran the
MI50-shaped kernels with dot8 emulated in software (`rq_dot8`: 8 shifts and multiply-adds per instruction).

**Matmul (`rq-w4a4-tc.cuh`).** An activation group is 64 inputs, exactly one `mma.m16n8k64.s4`, so the group's code
products come out of the tensor core as an exact int32 and the rest is the dot8 kernels' integer fold:
- The weight is the A operand (16 channels), the activation the B operand (8 tokens), so a decode or an 8-token verify
  is one n8 tile.
- Weights are repacked once, in place, into the MMA's fragment order: per 16 channels x 64 inputs, 32 lanes x 16 B,
  read with one coalesced load per lane and fed to the MMA as they are. Next to them one word per 8 channels holds the
  group's colsum and weight multiplier for two channels (12 + 4 bits each), so the repacked tensor still fits the
  blocks' 144 B.
- The zero-point term (8 - z) colsum goes into the MMA's accumulator, then tot += (k m sum) >> 4 as before.
- Turing runs the same fragments as four `m8n8k32` per group.
- Up to 64 tokens a warp holds one channel tile and all tokens; wider, a block of 8 warps holds 128 channels x 64
  tokens. K is split while the grid has fewer warps than the GPU holds.
- `RQ_TC=0` keeps the old kernels.

Bit-exact: all 56 W4A4 / W4A4H matmul tests pass at NMSE 0 against the CPU, and perplexity is identical to the last
digit with and without it (5.7949 over 6 chunks of 512, chunk by chunk).

| 3090, one matmul (test-backend-ops perf) | emulated dot8 | INT4 tensor cores |
|---|---|---|
| 17408x5120, 512 tokens | 5734 us | 764 us (7.5x) |
| 5120x17408, 512 tokens | 5635 us | 819 us |
| 17408x5120, 16 tokens | 272 us | 83 us |
| 17408x5120, 8 tokens (verify) | 150 us | 70 us |
| 17408x5120, 1 token | 54 us* | 68 us |

\* perf mode fuses three repeats of the same weight into one skinny launch, which reads it partly from L2 (ncu: 108 MB
from DRAM for three weights' worth, L2 hits 27%). Measured per byte from DRAM the two kernels stream at the same rate,
723 GB/s (tensor cores) and 752 GB/s (skinny), 77-80% of the 3090's 936.

The 27B end to end (llama-bench, f16 cache): **pp512 329 -> 1493 t/s, tg64 36.9 -> 38.0**. One DFlash2 request through

- Register double buffering of the weights, four groups ahead: decode 68 -> 77 us, prefill 760 -> 1138 us. It took

- More K splits (1 to 8): 67-72 us at every count.
- A per-warp rotation of the starting group, the gfx906 fix for DRAM channel conflicts (`RQ_SKINNY_ROT`): 66-73 us at

**Attention (`rq-fattn.cu`, CUDA).** The gfx906 kernel's numerics on tensor cores, for 1-16 query tokens, head size

- Q quantized to int4 per 32 values in q4_0's nibble order, the value of largest magnitude to -8.
- Q·K: one `mma.m16n8k32.s4` per q4_0 block (Q the A operand, 16 query rows; K the B operand, 8 tokens), the exact
  dot times dk dq in f32.
- Online softmax over 64-token tiles, P to f16, P·V with f16 `mma.m16n8k16` on V decoded as f16(d (q - 8)).
- The KV sequence split over the grid, combined by llama.cpp's `flash_attn_combine_results`.
- Prefill keeps llama.cpp's kernels with an f16 Q, as on gfx906.

  token where the tokenizer makes two), and the server tokenizes the returned text canonically. In one opencode task
  the token match ended 1089 and 612 tokens into two answers of 16k and 4.5k tokens, and the server re-processed
  16435 and 5097 tokens. Untruncated sampling (the published `--samplers temperature` with a client temperature
  above 0) makes these splits more likely.

Two server changes (both trees; on by default):
- **Text-level cache match** (`rq_adopt_cached_tokens`, `LLAMA_TEXT_MATCH=0` off): where the cached tokens and the
  new prompt spell the same bytes up to a common token boundary (within 64 tokens of the mismatch), the prompt takes
  the cached tokens for that span. A prompt cached with one word split into 3 tokens and sent back as text:
  6698 tokens re-processed without it, 8 with it, on the 3090 and on box 1 at TP4. In three opencode tasks it re-aligned
  35 requests (each conversation keeps its one non-canonical spot, so every later request passes through it).
- **Checkpoints while generating** (`LLAMA_GEN_CKPT_STEP`, default 4096 generated tokens, 0 off), for clients that
  do change a long answer. One character changed at 85% of an 11.7k-token answer, box 1 TP2: 11754 tokens re-processed
  in 18.8 s without them, 1499 in 3.1 s with them every 2048. Decode cost at every 2048 (8192 greedy tokens, two runs
  each): 3090 none (130.0 vs 128-129 t/s), TP2 0.3% (114.3 vs 114.6), TP4 0.75% (123.0 vs 123.9): the state is
  gathered from every GPU. Hence the default of 4096. `--ctx-checkpoints 0` (our long-prompt recommendation) turns
  these off along with the prompt checkpoints.

Also from his log: `-bs --samplers temperature` is greedy only when the client sends temperature 0. Agent clients
send 0.6-1.0 and then sample the whole distribution, without top-k / top-p; with `-sm tensor` or a tool grammar the
backend sampling it was there for is off anyway (both in his log). For agent use the default sampler chain is the
better choice. The `unknown type w4a4h` warning at load is harmless (the loader's file-type guess; the file's own type
key overrides it).

## Reproduce

- Build on an MI50 box: `rig/build_mx.sh`, which applies `patches/mx-llama.cpp-ruquant.patch` to mx-llama.cpp
  c4d12e2, ROCm 5.7 fixes included.
- OSTQuant: `.venv/bin/python accuracy/ostquant_qwen.py --out models/ost` (2.3 min/step on the 3090), then
  `accuracy/ost_pipeline.sh`, or the steps below with `--ost models/ost`.
- Model: `ruquant convert UD-Q8_K_XL.gguf OUT [--ost DIR] --types-from Q4_0.gguf --set ssm_out=q8_0
  --set output.weight=q8_0 --hessians DIR --wgroups`, with the Hessians from `ruquant hessian` on the same model
  rounded (no `--hessians`). No `setclip` needed: unset clips mean 1.0, the best at activation groups of 64.
- Drafter, with the target's R1 (`--ost DIR` or `--seed 1`):
  `ruquant drafter DFlash2-Q8_0.gguf Q4_0.gguf OUT --head w4a4h --linears w4a4h` (clips unset = 1.0).
- Bench: `rig/spec_bench.sh MODEL DRAFTER 5` with `SPEC=draft-dflash EXTRA="-bs --samplers temperature"`.
- TP: convert with `--rot-blocks 4` (model and drafter), run with `HSA_FORCE_FINE_GRAIN_PCIE=1
  GGML_META_TOKEN_GRAPH=0 GGML_CUDA_DISABLE_GRAPHS=1` and `-sm tensor -devd ROCm0`; acceptance over the four
  numeric variants with `GPUS=0,1,2,3 EXTRA="-sm tensor -devd ROCm0" python3 rig/acc_bench.py MODEL DRAFT 7`.
- Score on a box: `rig/score_box.sh`.
- Where a prefill forward goes, per GPU: rocprof traces of `llama-bench -n 0 -p 512 -r 1` on one GPU and under TP,
  then `python3 rig/tp_breakdown.py ONE.csv TP2.csv TP4.csv`.
